# Deploying the hosted demo

Backend on **Render** (Docker, free plan, WebSockets supported) using **Groq** for
the LLM. Frontend on **Vercel**. Everything is configured in the repo; the steps
below only need your accounts and your Groq key, which you paste into Render
yourself. Never commit it.

## 1. Groq key

1. Create an account at console.groq.com and create an API key.
2. In the console's model list, check that `llama-3.3-70b-versatile` is still
   offered. If not, pick another chat model and use its name for `LLM_MODEL` in step 2.

## 2. Backend on Render

1. render.com → **New → Blueprint** → connect the GitHub repo `agentflow`.
   Render reads [`render.yaml`](../render.yaml) and creates the `agentflow-api`
   web service from `backend/Dockerfile`.
2. When Render asks for the values marked "sync: false":
   - `GROQ_API_KEY`: paste your Groq key.
   - `CORS_ORIGINS`: leave empty for now (filled in step 4).
3. Wait for the first deploy, then open `https://<your-service>.onrender.com/health`.
   It should answer `{"status":"ok"}`. `/health/ready` should show
   `"llm": {"ok": true}`.

`METRICS_TOKEN` is generated by Render (Environment tab). `/metrics` needs
`Authorization: Bearer <token>`.

## 3. Frontend on Vercel

1. vercel.com → **Add New → Project** → import the same repo.
2. **Root Directory**: `frontend`. Vercel detects Vite from
   [`frontend/vercel.json`](../frontend/vercel.json).
3. Environment variable: `VITE_API_BASE_URL = https://<your-service>.onrender.com`
   (no trailing slash). The WebSocket URL (`wss://…`) is derived from it.
4. Deploy and note the URL, for example `https://agentflow-xyz.vercel.app`.

## 4. Allow the frontend in CORS

Render → `agentflow-api` → **Environment** → `CORS_ORIGINS =
https://agentflow-xyz.vercel.app` (comma-separate several origins; `*` is refused).
Save; Render redeploys.

## 5. Check the demo

Open the Vercel URL and run the three examples. The first request after a
quiet period can take up to a minute while the free instance wakes up; the
page says so.

## Demo limits (already configured)

| Limit | Value | Where |
| --- | --- | --- |
| Task creation | 10 per minute per IP | `backend/main.py` (`TRUSTED_PROXY_HOPS=1` reads the real IP behind Render's proxy) |
| Upload size | 5 MB | `MAX_FILE_SIZE_MB` |
| Retention | tasks and files deleted after 24 h | `RETENTION_HOURS` |
| Generated code | 5 s, 256 MB, isolated subprocess | `SANDBOX_*` |

## Known limits of the free plan

- No persistent disk: the SQLite history and uploads are lost on each redeploy
  or restart. That is acceptable for a demo; use a Render disk or Postgres otherwise.
- 512 MB of RAM. The server uses about 140 MB and each sandbox run is capped at
  256 MB. Two simultaneous memory-hungry runs could still exceed the limit, in
  which case Render restarts the service.
- If rate limiting ever applies to everyone at once, Render's proxy chain has
  changed: set `TRUSTED_PROXY_HOPS` to the number of proxies in front of the app.
